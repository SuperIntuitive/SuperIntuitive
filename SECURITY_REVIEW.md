# SuperIntuitive security review

Reviewed October 26, 2026, including the security changes already present from October 22. The threat model assumes attackers can read the full source, send arbitrary HTTP requests, obtain their own sessions, and know database record IDs. Security must depend on server-side authorization and private credentials, never on hidden source code.

This is a source review and an automated attack regression assessment. It is not a security certification or a guarantee that the application or a deployment cannot be compromised. The current changes were tested in disposable containers; the existing web and database services were not recreated.

## Findings addressed in this working tree

| Severity | Finding | Change |
| --- | --- | --- |
| Critical | Unpatched PHP can allow unauthenticated code execution before application code runs. | Require PHP 8.2.35+, 8.3.36+, 8.4.27+, or 8.5.12+ within those branches, reject prereleases and unknown branches, pin the Docker PHP release, and disable session upload progress in server configuration. |
| Critical during installation | Credentials entered into the installer could become executable PHP or SQL. | Encode PHP credentials with `var_export`, validate connection settings and identifiers, and encode SQL values as literals. |
| High during installation | The first public visitor could claim an unconfigured installation, including access to database connection testing. | Validate the installation key once in Step 1, rotate the PHP session and CSRF token, and require that authorized session plus CSRF protection for later setup actions. No secret is stored in the session or resent by later steps. Authorization expires after 30 idle minutes or 12 hours and is revoked by key rotation. Docker generates a private fallback key; a configured environment key takes precedence. Missing or weak keys disable authorization. Rate-limit authorization and setup requests separately. |
| High during installation | Domain traversal, symlinks, destructive reinstallation, setup races, or a missing schema could overwrite data or reopen setup. | Validate domains, reject symlinks and custom domain content, reuse only verified unchanged starter files without overwriting them, serialize installation attempts, preserve existing databases and users, and keep configured or locked installations closed when their database fails. |
| High | PHP treated the permission string `"false"` as an authorization grant. | Parse permission values as booleans and combine grants across roles. |
| High | Existing sessions retained privileges after role removal, account deactivation, or password changes. | Revalidate the account, password fingerprint, and active role assignments on application requests and generated assets. Reject old sessions without the new fingerprint. Clear cached page/editor data when permissions change. |
| High | Authentication and some record operations were not scoped to the current site. | Scope email and remember-token lookups to the current domain/subdomain. Require the record's entity scope for updates and password resets, reject ownership reassignment, and validate both ends of relations. Administrators remain trusted server operators, as explained below. |
| High | Assigned page roles were fetched without enforcement. Deactivating a required role could remove the restriction. | Enforce required roles before redirects or content retrieval, including when the required role has been deactivated. |
| High where entity operations are accessible | IDs, numeric and enum values, requested columns, relation ordering, and schema definitions could enter SQL without adequate validation. | Validate GUIDs and SQL identifiers, bind attribute and relation values, constrain schema field types and sizes, quote schema defaults, and derive language identifiers from the server's language list. |
| High | Request/setup logs, repository metadata, SQL backups, cookie jars, and private files could expose credentials or sessions. | Block HTTP access, disable debug dumps by default, remove tracked cookie jars, ignore private runtime/build inputs, and record session fingerprints instead of bearer cookies. Remove an embedded third-party key from commented source. Previously exposed values still require revocation. |
| High with media management access | Media promotion/recycling could traverse filesystem paths, and recycling interpolated its ID into SQL. | Restrict operations to the current site's media directories, reject traversal and symlinks, bind IDs, and scope record deletion. |
| High if a remember token is obtained | Remember tokens lacked a server-side lifetime, were stored as bearer values, and exceeded the database column length. | Enforce the 30-day lifetime, rotate tokens on restoration, and store a 128-bit SHA-256 digest that fits the existing schema. Plaintext legacy tokens no longer authenticate. |
| Medium | Login guesses were only delayed with sleeps, which occupied workers and could be bypassed with parallel sessions. Password-request emails had no shared limit. | Add file-locked limits shared by workers and browser sessions, based on the socket peer address: 10 login/password-verification attempts per 5 minutes, 5 password-request emails per hour, and 30 setup actions per 5 minutes. Ignore untrusted forwarded IP headers. |
| Medium | Authentication sessions lacked application-enforced expiry. | Enforce a 30-minute idle timeout and a 12-hour absolute lifetime. Regenerate IDs on login, password changes, invalidation, and logout. Revoke persistent tokens on logout and password changes. |
| Medium | Password changes could use another account's credentials; administrator-created accounts lacked the password policy. | Require the current account's credentials for self-service changes. Require 10 to 72 bytes with no NUL bytes for account creation, installation, and password changes. |
| Medium | Generated styles/scripts started sessions before applying strict cookie settings. Session HTML and editor assets could be cached. | Configure sessions before starting them and send private, no-store responses. Reject unauthorized editor requests. Validate language/Host values used by the application. |
| Medium | Uploaded active documents could execute scripts with the site's origin. | Sandbox uploaded content with a Content Security Policy in the supplied Apache configuration, retain MIME sniffing protection, and block server-side execution through both media URLs. Test actual image uploads, including when EXIF support is absent. |
| Medium | Plugin downloads allowed HTTP; installer review fields rendered input as HTML and displayed passwords. | Require HTTPS and certificate verification, disable redirects for downloads, render review values as text, mask passwords, and generate browser passwords with Web Crypto. |
| Medium | Docker exposed development services broadly, used excessive filesystem permissions, and accepted very large requests. | Bind web/phpMyAdmin to loopback, narrow runtime permissions, cap requests at 32 MB and files at 24 MB, hide PHP errors, and restrict backup filenames and permissions. |

The runtime minimums follow the [PHP security advisory](https://www.php.net/archive/2026.php). The October 23 advisory also recommends disabling `session.upload_progress.enabled`; the supplied PHP configuration does so. The October 26 Brotli advisory concerns Windows PHP packages; this stack uses Linux containers. These version checks do not inspect every bundled library or replace updating the runtime and restarting every worker. PHP 8.2 security support ends December 31, 2026, according to the [PHP support schedule](https://www.php.net/supported-versions.php).

## Deployment requirements and remaining limitations

- Rebuild and recreate the web container to activate image and Apache configuration changes. A source mount alone cannot update its PHP runtime or Apache rules. Existing authenticated sessions without the new fingerprint will be signed out at their next application request.
- Replace the documented development database passwords before public hosting, use HTTPS, and protect the installation key. For TLS termination or client IP restoration, configure the web server to trust only the actual proxy addresses. Arbitrary forwarded headers are deliberately ignored. Local HTTP tests verify HttpOnly/SameSite flags; public TLS termination and Secure cookies need deployment validation.
- Revoke the third-party API key previously present in commented source and rotate any credentials or sessions exposed by earlier logs, cookie jars, or repository history. Removing files and adding ignore rules cannot invalidate remote credentials or erase old commits. No external credential was revoked by this review.
- Administrators can author executable site content and install arbitrary plugins. Treat every administrator and plugin package as trusted server code. These controls do not establish isolation between mutually untrusted site administrators. Installed/custom plugins, plugin repository integrity, and uploaded packages need separate review.
- Media, including development/test variants, is served as public static content. Page-role checks do not protect direct media URLs. Do not store private attachments or secrets there; authenticated file delivery would be needed for that use case.
- Rate limits are per peer IP and shared within one installation's writable log directory. Multiple replicas need coordinated limits at a shared service or proxy. Distributed credential attacks and volumetric denial of service require infrastructure protection. MFA is not implemented by this work.
- Automatic schema repair and destructive reinstallation are disabled. Repair partial installations through a trusted operator with a backup.
- No independent penetration test, browser exploit assessment, container/OS vulnerability scan, production network review, or full plugin audit was completed. The account-recovery endpoint currently sends a notification rather than implementing a complete reset-token workflow. Commission a separate security assessment before relying on this for sensitive public-facing use.

## Validation

Run the commands in [README.md](README.md#security-regression-checks). The PHP checks cover runtime version boundaries, CSRF, installation keys, password/language validation, shared throttling, installer injection/traversal, denied permissions, unsafe schema definitions, remember-cookie expiry, and media paths. HTTP checks run against a disposable Apache/PHP/MariaDB stack and exercise real installation, authentication, authorization, cross-site record access, SQL payloads, actual uploads, private paths, session revocation/expiry, logout replay, and throttling.

All 110 PHP regression checks passed. All 91 HTTP checks passed with an existing database/user, and all 91 passed again with the privileged installer creating a new database/user. All 43 production PHP and generated PHP/JS/CSS syntax checks passed. Python compilation, shell syntax, Compose configuration, and `git diff --check` also passed. The unused legacy `core/test.php` scratch file is excluded from production linting and blocked from HTTP access. Both disposable test stacks were removed; the pre-existing services remain running.
