# Repository conventions

- Follow the existing one-file-per-entity structure. SIPL entity code belongs in `core_sipl/src/<Entity>.sipl`; PHP entity code belongs in `core/<Entity>.php`.
- Keep an entity's helpers together in that file, using clearly named functions or sections. Do not split them into manager, service, storage, host, or utility files unless the user explicitly requests that structure. Related PHP helper classes may share the entity file, as they do in `Entity.php`.
- Extend the existing code, formats, dispatcher, and UI. Avoid extra abstraction layers and unrelated rewrites.
- **WE DO NOT FIX ISSUES DOWN STREAM. WE FIX THEM AT THE SOURCE.** Diagnose the owning component before changing code. Runtime/library defects must be corrected in that runtime/library, with a minimal reproduction supplied to its project; do not add fallback implementations, compensating helpers, swallowed errors, or retries here to conceal them. Application and packaging defects owned by this repository are fixed here.
- Keep ownership explicit across the three projects: SIPL compiler/runtime changes belong in the SIPL repository; reusable CMS, editor, and plugin-framework changes belong in this repository; website content and deployment configuration belong in the website project. Fix shared CMS defects here first, then apply an explicit CMS update to a deployment. Never maintain a website-only fix for shared framework code.
- The public editor demo and its isolation belong in a separately distributed plugin, with deployment configuration owned by the website. Do not add demo code, routes, assets or settings to CMS core or either CMS installer. CMS updates must preserve installed plugin files, configuration and data.
- Use PHP for PHP-edition code and tooling, and SIPL for SIPL-edition code and tooling. Neither edition may require or execute the other backend. Do not introduce or use Python unless a necessary capability is unavailable in the project's languages; explain the concrete limitation first. Prefer native PHP/SIPL tools over adding another language dependency.
- `scripts/` is for the website's dynamic script skeletons and their existing assets, widgets, and metadata. Keep offline build, packaging, and upgrade tools in the existing `packaging/` directory. Never put Python, PowerShell, or generated bytecode in `scripts/`.
- Work in this main repository as the single source of framework code. Never create additional persistent copies, delivery trees, or running instances to diagnose an existing instance. Test fixtures must be temporary and automatically cleaned up.
- Before diagnosing or applying an update, identify the requested URL, listening process, source directory, and configuration. Building a ZIP does not update or reload a running deployment; never assume a different preview uses the requested site's code.
- Preserve existing functionality, plugin compatibility, authentication, authorization, CSRF checks, and private backend sources. Keep PHP and SIPL behavior consistent.
- Preserve configuration, credentials, media, installed plugins, CMS edits, and data. Do not restart or deploy the running website without explicit instructions.
- Build releases with the root `package.bat`. Verify changed behavior using the actual packaged edition. Distribute plugin ZIPs separately from CMS installers.
- Reuse existing tests and documentation. Do not add small helper files, duplicate guides, or reports for routine changes.
